# AI 협업 협업 기록

## 3A 진행·인계 기록

사용자는 네 확인사항에 답하지 않고 시작을 지시했다. ADMIN 승인·데모 연차·고정시간 및 상세 규칙은 설계 검토에서 결정했다. 구현/검증은 Codex, 디자인/이미지 검수는 Claude가 맡으며 실제 증거가 없는 디자인 효과는 기록하지 않는다.

첫 작업 기록에서 중간 완료 기록이 실제 완료로 처리되어 검증 작업와 검토단계가 진행됐고, 명령·작업 분담이 차단됐다. QA는 실제 일지와 최종 디자인 기록을 확인해 대기했다. 마무리 작업 기록에서도 프론트 검증 작업 중간 메시지가 done으로 잡히는 두 번째 사례가 발생했다. 설계 검토에서는 백엔드 완료와 프론트95/95·빌드 통과/Chromium 진단·Claude 미검수를 구분해 확인했다. 시스템 상태를 완료 근거로 쓰지 않는다.

설계 검토에서는 독립 문서·검수 스크립트 준비만 허용했고 Compose·README 스크린샷·커밋은 최종 인계까지 보류했다. 중간 질문/결함은 검토 기록, 완료 보고는 모든 기준 충족 후 한 번만 사용한다. 실행 시점이 다른 테스트 수를 합산하지 않고 최신 소스·명령·결과·미실행을 연결한다. [마무리 회의 초안](meetings/2026-10-16-phase3a-closing.md)에 경위와 재발 방지를 기록했다.

### 3A 최종 인계와 조기 완료 1~4차

| 사례 | 설계 검토 확인 사실·영향 | 대응 |
| --- | --- | --- |
| 1차 | 초기 검증 작업 중간보고가 done으로 잡혀 검증 작업까지 실제 완료 전에 종료 표시, 검토 단계의 실행·작업 분담 제한 발생 | 일지·검수물 직접 확인, QA미착수, 새 마무리 작업 기록 구성 |
| 2차 | 마무리 작업의 프론트 검증 작업 중간 메시지가 다시 done, 실제95/95·빌드 통과이나 Chromium/Claude미완료 | 독립 문서 준비만 허용, 실제검수 보류 |
| 3차 | 2단계 검증 작업 중간 메시지 done으로 QA조기배정, 디자인은1차이며 반영·재확인 미완료 | QA가 보고서와 최종일지 대조 후 대기 |
| 4차 | 3단계 QA업무가 실제검수·커밋 전 완료 표시됐음을 설계 검토에서 후속 단계에서 확인 | 설계 검토 인계물 검증 뒤 QA단독4단계 배정을 착수신호로 명문화 |

이는 설계 검토 확인과 실제 메시지의 관찰 기록이다. 시스템 내부에서 왜 중간 메시지를 완료로 처리했는지 소프트웨어 근본 원인은 확인하지 않았다. 검토 중 실행 보류은 정상 제한이며 ACL오류·실행환경 장애와 구분한다. webServer 무응답도 근본 원인은 미확정이다.

최종 프론트 근거는 15:36 타입·97/97 단일실행·빌드,15:37 목업5174 Chromium6/6,재촬영24장이다. Claude 최초22장·지적18개(D3A-01~18)→Codex반영→같은Claude24장재확인 순서이며 [design-review](design/design-review-phase3a.md)7.2에 동일ID를 연결했다. 높음/중간0, 새낮음N-01~07은Codex 담당이 근거·위험과 함께 수용했다(8절). 실측대비·스크린리더·실제API 등7.5의 미확인은 유지한다. 검수건수는 품질우열 수치가 아니다.

검증 작업 배정으로 QA착수가 허용돼 최종인계물을 실제 확인했다. 백엔드93/28·기존Compose,프론트97/6·목업·Claude검수와 QA의 실제Compose 결과는 각 실행주체/시각별로 구분한다. QA결과·미실행은 최종 검수보고서와 일지에 기록한다.

## 역할별 협업

Claude Code와 Codex가 설계·백엔드·프론트·문서QA를 나눠 맡고 교차 검수했다.

사용자는 Codex의 토큰 여유를 이유로 Codex 중심 운영을 요청했습니다. 이를 토큰 비용·사용량을 고려한 배분 전략으로 채택하되 실제 비용 절감 수치를 측정한 것은 아닙니다. Codex는 구현·문서·테스트를 주로 맡고 Claude Code은 조율·검수와 예외 상황을 맡습니다. 사용 가능한 개발 엔진은 Claude Code와 Codex이며 로그인 표시로 사용 가능 범위를 추정하지 않습니다.

제품의 Claude API/Ollama는 4단계 LLM 공급자입니다. 개발에 사용하는 Claude Code/Codex와 다른 개념이며 실행·검증 기록도 분리합니다.

## 회의와 작업

킥오프 1회, 단계 종료 회의, API·ERD 변경이나 충돌 시 수시 회의를 운영합니다. 상시 정기 회의는 없습니다. 킥오프에서는 두 차례 의견 수렴 후 설계 검토에서 범위·권한·계약·소유권을 결정했습니다. 계약 변경은 설계 검토 질문→양 팀 공유→문서 갱신 절차를 따릅니다.

작업마다 받은 지시, 수행 내용, AI 제안 채택·수정·기각 근거, 문제·해결, 실제 검증 명령과 결과를 기록합니다. 테스트 미실행을 통과로 표현하지 않습니다. AI가 내린 결정을 사람이 판단했다고 쓰지 않습니다. 사람의 결정은 실제 사용자 발언을 근거로 남깁니다. 비밀값·토큰·실존 인물 정보는 기록하지 않습니다.

## 실제 운영 이슈: 세션 종료와 회의 재개

개발 세션이 중단되어 검토를 재개했다. 정확한 원인과 복구 경위는 직접 확인하지 못해 특정 주체가 해결했다고 단정하지 않았다.

재개 후 기존 자료와 실제 산출물을 대조했다. 확인되지 않은 원인이나 복구 조작을 추정하지 않았다.

또한 1차 전달문에는 상세 기능 목록이 빠져 있었지만 의견 제출 도구 응답의 기존 대화에서 범위를 복원했습니다. 2차에 이를 정정하여 사용자에게 같은 범위를 다시 묻지 않도록 제안했습니다.

## 1단계 실제 운용 사례

- **계약 질의 2건:** 백엔드 에서 EMPLOYEE의 부서·직급 조회 예외와 성공 상태 코드, 퇴사자 수정·중복 퇴사 처리를 확인했습니다. Codex의 400 제안은 설계 검토에서 409 EMPLOYEE_RETIRED로 수정했습니다. 에서는 백엔드 초기 과업의 Compose 범위를 MySQL/backend로 확정하고 프론트 통합을 별도 과업으로 나눴습니다. 이는 AI 간 판단·조율이며 사용자의 직접 코드 검수로 표현하지 않습니다.
- **권한·셸 이슈:** 백엔드 기록의 CreateProcessWithLogonW 1326, 프론트 기록의 Access denied/쓰기 실패는 필요한 명령에 승인된 실행 경로를 사용해 해결했습니다. 문서QA도 Docker named pipe 접근과 Node 결과 파일 쓰기에서 권한 거부를 확인하고 승인 실행으로 진행했습니다. Git 소유자 차이는 명령 단위 safe.directory로 처리하며 전역 신뢰 설정을 바꾸지 않았습니다.
- **Testcontainers 호환:** 백엔드는 Docker 29.4.0에서 Testcontainers 1.21.3 연결이 HTTP 400으로 실패한 뒤 공식 릴리스 근거로 1.21.4로 갱신하고 실제 MySQL 테스트를 통과했습니다. 문서QA는 해당 개발일지와 보고서를 근거로 인용하며 이번에 같은 테스트를 재실행했다고 쓰지 않습니다.
- **병행 구현과 통합:** 확정 API를 기준으로 백엔드와 프론트가 별도 디렉터리에서 구현했습니다. 프론트의 목업 통과 후 백엔드가 Compose 3서비스를 연결하고, 문서QA가 실제 Chromium/API 20개 시나리오를 검수했습니다. 목업과 실제 서버 검증을 별도 증거로 남겼습니다. 소스 변경은 각 팀, 공통 문서와 최종 커밋은 문서QA가 맡았습니다.

## 2단계 엔진 재배분 및 실제 이슈

사용자 발언: "코덱스가 코딩작업은 잘한다고 생각하지만 디자인 작업은 다른 ai가 낫다고 생각하거든", "물론 이미지 생성은 코덱스가 좋긴 해". 설계 검토에서는 Claude 디자이너의 디자인/검수와 Codex의 구현/테스트를 분담했습니다. 초기 Codex 중심 원칙을 작업 성격별 배분으로 조정한 결정이며 제품 LLM 공급자와 별개입니다.

[디자인 검수](design/design-review-phase2.md) 7절 근거: Claude 시안→Codex 구현→Claude 이미지 검수3회→Codex 반영. 지적28건 중 해결24/부분수용1/대안수용3, 높음·중간 잔여0. 최종30장 중 변경8장을 마지막에 직접 확인하고 나머지는 직전 판정을 유지했습니다. 모바일 상단 바, 오류 중복, 복귀 링크·확인 대화상자가 실제 변경 사례입니다. 이는 엔진 우열·비용절감 수치가 아니며 목업 디자인 검수가 실제 DB/파일/API나 실측 대비·스크린 리더 검증을 대신하지 않습니다. [ADR0002](adr/0002-task-based-engine-allocation.md).

문서QA 실행 중 명령 반환 지연을 런타임 문제로 의심해 검토 기록에 확인했습니다(). 설계 검토에서는 실제 Docker 빌드·MySQL 기동 진행을 확인했고, 기존 명령 결과를 회수해 중복 up 없이 이어갔습니다. apply_patch의 --windows-sandbox-private-desktop 인자 오류는 별개였으며 설계 검토 안내와 권한 승인 후 PowerShell Set-Content로 문서를 작성했습니다. 권한을 우회하거나 ACL을 바꾼 것이 아니라 승인된 실행 경로를 사용했습니다. 파일 검수 스크립트의 xlsx 버튼명 불일치도 QA 선택자를 수정 후 재실행했으며 앱 결함으로 분류하지 않았습니다.
