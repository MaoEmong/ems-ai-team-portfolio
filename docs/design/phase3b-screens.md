## 0. 공통 원칙 (3B 전 화면)

| 원칙 | 화면 규칙 |
|---|---|
| 판정·계산은 서버 | 프론트가 계산하지 않는 것: 급여 금액(`grossPay`·`deductions[].amount`·`totalDeductions`·`netPay`), 생성 대상, 평가 `finalScore`·`grade`, 상태 전이. 화면 계산은 표시 집계와 단위 변환만 한다. 표시 집계는 "(표에서 센 수)"로 쓰고, 단위 변환은 rateBps → % 하나다 |
| 버튼은 allowedActions만 | 급여 월(`RECALCULATE`·`CONFIRM`), 평가 주기(`EDIT`·`OPEN`·`CLOSE`), 평가서(`SAVE_SELF`·`SUBMIT_SELF`·`SAVE_MANAGER`·`SUBMIT_MANAGER`·`REASSIGN_REVIEWER`) 버튼은 응답 `allowedActions`에 있을 때만 그린다. 없으면 숨기고 필요하면 muted 이유 글자 |
| 분기는 code | 오류 문구는 `code`로 고르고 `message`는 보조로 쓴다(계약 §1) |
| 409 후 안내·재조회 | 모달·띠로 안내한 뒤 해당 리소스를 다시 조회한다. 입력값은 모달을 닫기 전까지 유지 |
| 스냅샷은 스냅샷이라고 쓴다 | 명세·월 상세·평가 항목·발령 이력은 생성(처리) 당시 저장값이다. "과거 상태를 복원한 값이 아님"을 안내한다(§11.7) |
| 민감 정보 최소 노출 | 금액·점수·코멘트·등급은 토스트·role=status·`<title>`·브레드크럼·URL에 넣지 않는다. 3B 급여·평가 알림은 없다(계약 §1) |
| 사원 식별 | `이름 (사번)`. 사번 필드는 `employeeNo` |
| 데모 고지 | 급여 화면·명세 상단에 `demoNotice`(서버 문구 우선). 명세가 없는 화면은 계약 §4의 고정 문구 "포트폴리오용 데모 급여 — 실제 세법·4대보험 산정 아님" |
| 다운로드 없음 | 급여 파일 다운로드·내보내기·인쇄 버튼을 만들지 않는다(계약 범위 제외) |
| 접근성 | design-system §6 그대로. 트리는 §1.4 |

## S0. 메뉴 구조

```
내 업무                     관리 (ADMIN)
 출퇴근·근태                 대시보드
 휴가 신청·내 휴가            사원 관리
 조직도          ← 신규       조직 관리(부서 계층) ← 기존 "부서 관리" 확장
 내 급여명세서    ← 신규       직급 관리
 내 평가         ← 신규       직책 관리     ← 신규
 내 정보                     근태 관리 · 휴가 결재
                             급여 관리     ← 신규
                             평가 관리     ← 신규
                             감사 로그
```
- 화면 경로는 프론트 라우트 제안이다. API 경로는 각 절에 적었다.
- "내가 평가할 사원"은 `GET /evaluations/assigned` 결과가 1건 이상인 사용자에게 "내 평가" 화면의 두 번째 탭으로 보인다. 결과가 0건이면 탭을 숨긴다(배정이 없는 ADMIN은 탭 없음).
- 사이드바가 길어지면 design-system §10.2 내부 스크롤 규칙을 쓴다. 브레드크럼에는 그룹("내 업무"/"관리")을 넣는다.

## S1. 조직도 (`GET /organization`, 인증 사용자 누구나)

### 1.1 데이터와 조립
- 응답: `departments[{id,name,parentId}]`(name ASC,id ASC), `employees[{id,employeeNo,name,department{id,name},position{id,name,level},jobTitle{id,name}|null,onLeave}]`(employeeNo ASC,id ASC). 둘 다 **평탄 배열**이다.
- 사원은 ACTIVE·ON_LEAVE만 온다(퇴사 제외). 빈 부서도 온다. 이메일·전화·급여·평가는 없다.
- **트리는 화면이 parentId로 조립한다.** 표시 구조 변환이며 도메인 판정이 아니다.
  1. `parentId = null` → 루트. 루트는 여러 개일 수 있다.
  2. parentId가 배열에 없는 부서 → 루트로 표시(숨기지 않음). 서버가 막는 전제이므로 개발 콘솔 경고만.
  3. 형제 순서는 서버 배열 순서(name ASC,id ASC).
  4. 순환은 서버가 409 `DEPARTMENT_CYCLE`로 막는 전제다. 조립 코드는 방문 표시로 무한 루프를 막는다.
  5. 사원은 `employee.department.id`로 부서에 붙인다. 직속 인원 수는 사원 배열에서 센 **표시 집계**다.
- `employee.department`가 null일 수 있는지는 `〈계약 공백 G-1〉`이다. null이 오면 트리 맨 아래에 "부서 미지정 (n)" 가상 노드를 둔다. 오지 않으면 노드도 없다.

### 1.2 데스크톱 배치
```
홈 / 내 업무 / 조직도
조직도
부서 계층과 소속 사원을 확인합니다. 재직·휴직 사원만 표시하며 퇴사자는 표시하지 않습니다.

[부서·사원 검색 ________]  [모두 펼치기] [모두 접기]        보기: (●) 트리  ( ) 목록
┌ 부서 트리 (320px) ──────────┐┌ 선택한 부서: 가상플랫폼부 ───────────────────────┐
│ ▾ 가상개발부  (0)            ││ 상위: 가상개발부                                    │
│     가상플랫폼부 (4) ◀ 선택   ││ 소속 4명 · 휴직 1 (표에서 센 수)                     │
│     가상QA부 (0)  빈 부서     ││ 이름 (사번)            직급       직책       상태     │
│ ▸ 가상경영부  (2)  ← 두 번째 루트│ 가상사원001 (DEMO001)  가상대리   가상팀장    재직     │
└────────────────────────────┘│ 가상사원007 (DEMO007)  가상사원   —          [휴직]   │
                               │ 하위 부서: 없음                                    │
                               └──────────────────────────────────────────────┘
```
- 괄호 숫자는 직속 인원이다. 하위 포함 인원은 만들지 않는다.
- 빈 부서: muted "빈 부서". 선택하면 "이 부서에는 재직·휴직 사원이 없습니다."
- 직책: `jobTitle=null`이면 "—". 상태: `onLeave=true`이면 [휴직] 배지, false이면 "재직" 글자(배지 없음).
- 표기 안내 `<details>`: "직책은 조직 내 역할 표시이며 시스템 권한을 주지 않습니다. 휴가 결재는 관리자 계정이 합니다."

### 1.3 목록 보기 (트리 대체, 모바일 기본)
- 같은 데이터를 중첩 `<ul>`로 그린다. 들여쓰기 16px/단계에 시각 숨김 "n단계" 텍스트를 붙인다. ARIA tree 없이도 완전히 쓸 수 있어야 한다.
```
가상개발부 — 0명
  가상플랫폼부 — 4명
  가상QA부 — 빈 부서
가상경영부 — 2명
```

### 1.4 트리 키보드·접근성
- `role=tree/treeitem/group`, `aria-expanded·aria-level·aria-setsize·aria-posinset`, 로빙 tabindex.
- 키: ↑↓ 이동, → 펼침 또는 첫 자식, ← 접음 또는 부모, Home/End, Enter/Space 선택.
- 선택이 바뀌면 polite로 한 번 알린다: "가상플랫폼부 선택, 소속 4명".
- 검색은 받은 배열 안에서 하는 표시 필터다(부서명·이름·사번). 일치하면 조상 노드를 펼치고 `<mark>`로 강조, 결과 수를 role=status로 알린다.
- 깊이 제한이 계약에 없다(서버는 순환만 막음). 화면은 5단계까지 들여쓰고, 더 깊으면 "› 상위 경로" 글자로 보완한다.

### 1.5 모바일 (390)
- 목록 보기가 기본이다. 부서를 누르면 부서 상세로 넘어간다: "‹ 상위: 가상개발부", 사원 카드(1행 이름 (사번) + [휴직], 2행 직급 · 직책), 하위 부서 목록.
- 트리 보기는 모바일에서 숨긴다.

### 1.6 상태
- 로딩 스켈레톤 + role=status "조직도를 불러오는 중…". 401은 기존 로그인 흐름.
- 부서 0: "등록된 부서가 없습니다." (ADMIN에게만 [조직 관리로 이동])
- 오류: danger + [다시 시도].

## S2. 조직 관리 — 부서 계층 편집 (ADMIN, `/departments`)

### 2.1 배치
```
홈 / 관리 / 조직 관리
조직 관리
상위 부서를 지정해 계층을 만듭니다. 상위 부서를 비우면 최상위 부서가 됩니다.
부서 구조를 바꿔도 사원의 소속 부서는 자동으로 바뀌지 않습니다.
[+ 부서 추가]
부서              상위 부서         설명           관리
가상개발부         — (최상위)        합성 부서       [수정] [삭제]
  가상플랫폼부     가상개발부        …              [수정] [삭제]
```
- 계층 표는 `GET /departments`(name,id 순) 배열을 S1과 같은 규칙으로 들여쓰기 조립해 그린다. 드래그 편집은 없다.
- 직속 인원 열은 이 응답에 사원 수가 없어 만들지 않는다. 필요하면 조직도 화면에서 본다.

### 2.2 추가·수정 모달 (560px)
```
┌ 부서 수정 ───────────────────────────────────────┐
│ 부서 이름 *  [가상플랫폼부        ]   1~100자          │
│ 설명         [합성 부서           ]   0/500자          │
│ 상위 부서     [가상개발부 ▾]  (맨 위 옵션: "없음 — 최상위") │
│ ⓘ 상위를 바꾸면 이 부서의 하위 부서도 함께 옮겨집니다.     │
│   사원의 소속 부서는 바뀌지 않습니다.                     │
│                                   [취소] [저장]     │
└─────────────────────────────────────────────────┘
```
- 전송: `{name, description, parentId}`. "없음"이면 `parentId: null`.
- 상위 select 옵션은 들여쓰기한 경로 텍스트("가상개발부 › 가상플랫폼부")로 쓴다. 자기 자신과 자기 하위 부서는 **비활성**으로 두고 옵션 끝에 "(자기 또는 하위 부서)"를 붙인다. 표시 편의일 뿐이며 최종 판정은 서버 409다.
- 오류(code 분기):

| code | 위치 | 문구 |
|---|---|---|
| DEPARTMENT_CYCLE | 모달 안 상위 필드 아래 | 자기 자신이나 하위 부서를 상위 부서로 지정할 수 없습니다. |
| DUPLICATE_NAME | 이름 필드 아래 | 같은 이름의 부서가 있습니다. |
| 404 (없는 부모) | 모달 상단 | 선택한 상위 부서를 찾을 수 없습니다. 목록을 다시 불러왔습니다. (재조회) |
| VALIDATION_ERROR | fieldErrors | 서버 reason |

- 성공: 재조회, 해당 행 2초 하이라이트, role=status "가상플랫폼부를 저장했습니다."

### 2.3 삭제 (확인 모달 440px → `DELETE /departments/{id}` 204)
| code | 문구 |
|---|---|
| DEPARTMENT_HAS_CHILDREN | 하위 부서가 있어 삭제할 수 없습니다. 하위 부서를 먼저 옮기거나 삭제하세요. |
| DEPARTMENT_IN_USE | 소속 사원(퇴사자 포함)이나 발령 이력이 있어 삭제할 수 없습니다. |
- 삭제 버튼은 미리 숨기지 않는다(판정은 서버).

### 2.4 모바일
- 카드: 1행 `└ 가상플랫폼부`(들여쓰기 최대 3단계, 더 깊으면 경로 글자), 2행 상위 · 설명 한 줄 말줄임, 3행 [수정] [삭제] 44px.

## S3. 직책 관리 (`/job-titles`)

```
홈 / 관리 / 직책 관리
직책 관리
조직 내 역할(예: 팀장)을 관리합니다. 직급과 별개이며 시스템 권한을 주지 않습니다.
사원당 0~1개이며 같은 직책을 여러 사원이 가질 수 있습니다.   [+ 직책 추가]
이름        설명           관리
가상팀장    합성 직책       [수정] [삭제]
```
- 목록: `GET /job-titles`(name ASC,id ASC). 열은 계약 필드인 이름·설명만이다. 지정 인원 열은 계약 필드가 없어 만들지 않는다.
- 모달: 이름 1~100, 설명 ≤500.
- 오류 문구:
  - `DUPLICATE_NAME`: "같은 이름의 직책이 있습니다."
  - `JOB_TITLE_IN_USE`: "현재 사원 또는 과거 발령에서 사용 중인 직책이라 삭제할 수 없습니다."
  - 404: "직책을 찾을 수 없습니다." + 재조회
- 사원 등록 폼과 엑셀 양식은 바꾸지 않는다. 신규 사원의 초기 직책은 null이며, 직책은 발령으로만 정한다.
- 모바일: 2단계 직급 관리 카드 그대로.

## S4. 발령 — 직책 지정·변경·해제 (`POST /employees/{id}/appointments`)

### 4.1 모달 (2단계 발령 모달 확장)

└──────────────────────────────────────────────────────────┘
```
- 계약상 `departmentId`·`positionId`는 **항상 필수**다. 그래서 2단계의 "변경 체크" 방식 대신 **현재 값을 미리 채운 select**를 쓴다. 바꾸지 않으면 현재 값이 그대로 전송된다.
- 직책 체크박스:
  - 꺼짐 → `changeJobTitle: false`(또는 생략), `jobTitleId`는 보내지 않는다.
  - 켜짐 + 지정 → `true` + 선택한 ID.
  - 켜짐 + 해제 → `true` + `null`.
  - 현재 직책이 null이면 "직책 해제" 옵션을 비활성으로 두고 "현재 직책이 없습니다"라고 쓴다(바뀌는 게 없으므로).
- **변경 요약 줄**은 고른 값을 문장으로 되보여 준다(계산 아님). 세 값이 모두 현재와 같으면 요약에 "바뀌는 항목이 없습니다." warning을 띄운다. 서버도 400을 준다.
- 오류(code 분기):

| code | 문구 |
|---|---|
| VALIDATION_ERROR (모두 동일) | 부서·직급·직책 중 하나 이상 바꿔야 발령을 등록할 수 있습니다. |
| VALIDATION_ERROR (날짜) | fieldErrors → 발령일 아래 |
| EMPLOYEE_RETIRED | 퇴사한 사원은 발령할 수 없습니다. (재조회) |
| 404 (직책) | 선택한 직책을 찾을 수 없습니다. 직책 목록을 다시 불러왔습니다. |

### 4.2 발령 이력 표 (`fromJobTitle`/`toJobTitle` 추가)
| from | to | 표시 |
|---|---|---|
| A | B | `A → B` |
| A | null | `A → 해제` |
| null | B | `— → B` |
| null | null | `—` |
| A | A | `A` (변경 없음, muted) |

- **null은 항상 "—"** 로 쓰고 "없음"이라고 쓰지 않는다. 계약 §3에 따라, 과거 이력의 null이 "직책 없었음"을 뜻하는지 "기록 이전"을 뜻하는지 구분하지 않는다.
- 표기 안내: "—는 직책 정보가 없음을 뜻합니다. 직책 기능 도입 전 발령은 직책이 기록되지 않았습니다."
- 스냅샷 캡션은 2단계 문구를 확장한다: "부서·직급·직책 이름과 등록자는 발령 당시 정보입니다."
- 퇴사 때 직책 해제는 발령을 만들지 않는다(계약 §3). 그래서 이력 표에 "퇴사로 해제" 행이 없다. 이 사실은 감사 로그(EMPLOYEE_RETIRE 전후 jobTitle)에서 본다. 퇴사 확인 모달 문구에 "현재 직책은 해제되며 발령 이력은 그대로 남습니다."를 덧붙인다.

### 4.3 사원 상세·수정
- 상세 기본 정보에 "직책"(EmployeeView `jobTitle`, null이면 "—")을 넣는다. 수정 화면에 직책 입력은 없고 안내 "직책은 발령으로 변경합니다."만 둔다.
- 수정 PUT에 다른 jobTitleId를 보내면 409 `APPOINTMENT_REQUIRED`가 난다. 화면은 jobTitleId를 보내지 않는다. 2단계 APPOINTMENT_REQUIRED 문구를 재사용한다.
- 사원 목록의 직책 열·필터는 계약에 없어 만들지 않는다.

## S5. 급여 설정 (ADMIN, `GET/PUT /employees/{id}/salary-setting`)

### 5.1 위치 — 사원 상세 안의 "급여 설정" 블록
- 계약에는 **사원별 단건 조회·저장만** 있다. 전체 사원의 설정 목록이나 "미설정 사원" 조회 API는 없다(`〈계약 공백 G-3〉`).

│ ⓘ 포트폴리오용 데모 급여 — 실제 세법·4대보험 산정 아님        │

│ 공제율  4.50% · 3.50% · 3.00% (고정) · 산식 DEMO_V1            │
│ 바꾼 설정은 이후 생성·재계산하는 급여에만 적용됩니다.              │

```
- GET이 404면 "급여 설정이 없습니다. 설정이 없으면 이 사원이 대상인 월 급여를 생성할 수 없습니다." + [급여 설정 등록]. 이 경우 warning 배지 [미설정].
- 공제율은 응답 `deductionRates`(bp 배열)를 %로 바꿔 쓴다. 산식은 `formulaVersion` 그대로.
- 블록은 ADMIN만 본다. EMPLOYEE의 내 정보 화면에는 없다.

### 5.2 설정 모달 (440px, PUT → 200)
- 기본급·수당 각각 `inputmode=numeric`. 표시는 쉼표, 전송은 정수.
- 클라이언트 검사: 정수, 0 이상, 1,000,000,000 이하. 문구 "0 이상 1,000,000,000 이하 정수로 입력하세요." 서버 400 fieldErrors가 최종이다.

- 성공: role=status "급여 설정을 저장했습니다." **금액은 쓰지 않는다.** 감사 로그에도 금액이 남지 않는다(계약 §6).

## S8. 평가

### 8.1 계약 요약
- 주기 상태와 허용 동작:
  - DRAFT: EDIT·OPEN
  - OPEN: CLOSE, 평가 작성, 미확정 재배정
  - CLOSED: 조회만
- 평가서 상태와 동작:

| 평가서 상태 | 본인 | 배정 평가자 |
|---|---|---|
| SELF_DRAFT | SAVE_SELF·SUBMIT_SELF | 조회 |
| SELF_SUBMITTED | 조회 | SAVE_MANAGER·SUBMIT_MANAGER |
| MANAGER_DRAFT | 조회 | SAVE_MANAGER·SUBMIT_MANAGER |
| FINALIZED | 공개 결과 조회 | 조회 |

- 평가서는 주기를 OPEN할 때 생성되며, 그때 항목이 스냅샷된다.
- `incomplete` = CLOSED && state≠FINALIZED.
- 공개 전 본인 상세에는 `managerAnswers`·`finalScore`·`grade` **키 자체가 없다**.
- 상세(`GET /evaluations/{id}`)는 본인 또는 배정 평가자만 볼 수 있다. **다른 ADMIN은 404**다.
- 점수·등급: `finalScore`는 관리자 점수 평균을 소수 둘째 자리로 반올림한 값, `grade`는 S/A/B/C/D(서버 저장값). 자기평가 점수는 들어가지 않는다.

### 8.2 평가 관리 — 주기 목록 (`GET /evaluation-cycles`, ADMIN)
```
홈 / 관리 / 평가 관리
평가 관리                                                  [+ 평가 주기 만들기]
주기 이름              기간(표시용)               상태
합성 2026 하반기        2026-07-01 ~ 2026-12-31   [진행]    [열기]

- 주기DTO에 완료 수가 없어 "완료 n/m" 열은 만들지 않는다.

### 8.3 주기 편집 (DRAFT, `POST /evaluation-cycles` · `PUT /evaluation-cycles/{id}` 전체 교체)
```
홈 / 관리 / 평가 관리 / 합성 2026 하반기
합성 2026 하반기  [준비]                         [저장] [주기 열기]   ← EDIT / OPEN
이름 *  [합성 2026 하반기]   시작일 * [2026-07-01]  종료일 * [2026-12-31] (표시용 · 자동 마감 없음)
[평가 항목] [대상·평가자]

(평가 항목 탭) 모든 항목의 가중치는 같습니다. 1~20개. 주기를 열면 항목이 고정됩니다.
순서  항목 이름                관리
1     업무 수행               [↑] [↓] [수정] [삭제]
2     협업                    [↑] [↓] [수정] [삭제]
[+ 항목 추가]

(대상·평가자 탭) 1명 이상. 대상은 재직·휴직 중이고 입사일이 지난 사원.
대상 사원                 평가자                          관리
가상사원002 (DEMO002)     가상관리자 (ADMIN001)  [변경]     [제거]
[+ 대상 추가]
```
- **편집은 화면 안에서 모았다가 [저장] 한 번에 PUT(전체 교체)** 한다. 저장하지 않은 변경이 있으면 상단 warning "저장하지 않은 변경이 있습니다."를 띄우고, 화면을 떠날 때 확인한다. [주기 열기]는 저장되지 않은 변경이 있으면 먼저 저장하라고 안내한다(열기 전에 서버 상태와 맞추기 위함).
- 항목 순서는 [↑][↓]로 바꾼다. 전송하는 `sortOrder`는 표시 순서대로 1, 2, 3…을 다시 매긴다(중복 불가 규칙 충족, 0~10000). 이동 후 role=status "업무 수행, 2번째로 이동".
- 클라이언트 검사: 이름 1~100, 시작 ≤ 종료, 항목 1~20개·이름 1~100, 대상 1명 이상, 같은 대상 중복 불가. 서버 400 fieldErrors가 최종이다.
- 평가자 선택 모달:
  - 후보는 "대상자가 아닌, 로그인 가능한 재직 ADMIN 중 입사일이 지난 사원"이다.
  - 이 후보 목록을 주는 API가 계약에 없다(`〈계약 공백 G-6〉`). 화면은 후보를 추정해 걸러 내지 않는다. 구현 방법은 공백 해소 후 정한다.
  - 대상 본인을 고르면 클라이언트에서 "본인은 자기 평가자가 될 수 없습니다."로 막는다(계약 403의 선검사).
  - 서버 409 EVALUATION_REVIEWER_INVALID → "선택한 평가자는 배정할 수 없습니다. 로그인 가능한 재직 중 관리자이며 대상자가 아닌 사람만 배정할 수 있습니다."
- **사원 식별과 데이터 흐름(v1.1 확정)**:
  - **읽기**: 편집 화면은 `GET /evaluation-cycles/{id}`로 불러온다. 이 응답의 `assignments[]`는 조회 전용 요약 `{evaluationId, employee{id,employeeNo,name}, reviewer{…}, state, incomplete, allowedActions}`이다.
    - DRAFT에서는 `evaluationId=null`, `state=null`, `incomplete=false`, `allowedActions=[]`이다.
    - 그래서 DRAFT 편집 표에는 평가서 상태 열과 [평가자 변경] 버튼이 없다. 행 관리는 [평가자 변경(편집)]·[제거]이며, 화면 안 편집이다.
    - `이름 (사번)`은 `employee`·`reviewer` 참조로 표시한다.
  - **쓰기**: [저장]은 `PUT`(전체 교체)이며 입력은 여전히 `{employeeId, reviewerId}` ID 쌍이다. 화면은 요약의 `employee.id`·`reviewer.id`를 ID 쌍으로 바꿔 보낸다(표시 형태 변환).
  - **저장 후**: POST/PUT 응답은 기존 주기DTO(ID 쌍 assignments)다. 그래서 저장에 성공하면 `GET /evaluation-cycles/{id}`를 다시 불러 참조형으로 다시 그린다. ID 쌍 응답으로 표를 그리지 않는다.
  - **새 주기 만들기(POST)**: 처음 저장 전에는 서버 참조가 없다. 대상·평가자 선택 때 확인한 사원 정보를 화면에 둔다. 선택 출처는 G-6이며, 구현 최소안은 ID 입력 후 기존 사원 조회 확인이다(§12A).
- [주기 열기] 확인(440px): "주기를 열면 평가 항목 {n}개가 고정되고 대상자 {m}명의 평가서가 만들어집니다. 항목과 대상은 다시 바꿀 수 없습니다(평가자 재배정만 가능)." [취소] [주기 열기](primary). n·m은 화면이 가진 저장 상태에서 센 표시 집계다.
- 오류: 409 EVALUATION_STATE_CONFLICT "주기 상태가 바뀌었습니다. 최신 상태를 불러왔습니다." + 재조회.

### 8.4 주기 상세 (OPEN·CLOSED, ADMIN)
```
합성 2026 하반기  [진행]                                      [주기 종료]  ← CLOSE
기간 2026-07-01 ~ 2026-12-31 (표시용 · 자동 마감 없음)
[평가 항목(고정)] [대상·평가자] [진행 현황]
```
- 항목 탭: 읽기 전용, info "주기를 연 시점의 항목으로 고정되었습니다."
- 대상·평가자 탭과 진행 현황 탭: 평가서별 상태·`incomplete`·[평가자 변경](`REASSIGN_REVIEWER`)을 보여야 한다.
  - **출처(v1.1 확정)**: `GET /evaluation-cycles/{id}`(ADMIN)의 `assignments[]` 조회 전용 요약이다. 새 관리 목록 API는 없다.
    - `evaluationId`: OPEN부터 값이 있다.
    - `employee{id,employeeNo,name}`, `reviewer{id,employeeNo,name}`
    - `state`, `incomplete`(CLOSED && state≠FINALIZED)
    - `allowedActions`: OPEN이고 미확정이면 `["REASSIGN_REVIEWER"]`, FINALIZED이거나 주기 CLOSED이면 `[]`
  - 정렬은 서버 순서(employee.employeeNo ASC, 배정 ID ASC)를 그대로 쓴다. 필터는 주기 단위뿐이다. 이름·사번 검색은 받은 배열 안의 표시 필터다.
  - 점수·코멘트·등급·답변은 응답에 없다. 이 탭에도 그런 열을 만들지 않는다.
  - 주기 관리 ADMIN은 배정 관계가 없어도 이 요약에서 재배정할 수 있다(`PUT /evaluations/{evaluationId}/reviewer`).
    - 평가서 상세(`GET /evaluations/{id}`)의 404 정책은 그대로다(계약 v1.1). 그래서 **행에 상세 링크를 두지 않는다.** 대상 이름은 링크가 아닌 텍스트다.
  - [평가자 변경]은 행 `allowedActions`에 `REASSIGN_REVIEWER`가 있을 때만 보인다. 없으면 FINALIZED 행에 muted "(변경 불가)", CLOSED 주기에는 아무것도 쓰지 않는다.
```
(대상·평가자 탭 — assignments 요약, v1.1)
대상 사원               평가서 상태               평가자                    관리
가상사원002 (DEMO002)   [자기평가 제출]           가상관리자 (ADMIN001)       [평가자 변경]  ← REASSIGN_REVIEWER
가상사원003 (DEMO003)   [최종 확정]               가상관리자 (ADMIN001)       (변경 불가)
(CLOSED) 가상사원004    [자기평가 작성 중][미완료]   …                          —
```
- 요약 항목은 계약상 `{id, cycle, employee, reviewer, state, incomplete, allowedActions}`만 있고 점수·코멘트·등급은 없다. 이 화면에도 넣지 않는다.
- [주기 종료] 확인(440px):
  - 문구: "주기를 종료하면 더 이상 평가서를 작성·재배정할 수 없습니다. 최종 확정되지 않은 평가서는 현재 상태 그대로 '미완료'로 남습니다. 되돌릴 수 없습니다."
  - 확인 체크박스를 두고 버튼은 [종료](danger-solid).
  - 미완료 예상 건수는 `assignments[]`에서 state≠FINALIZED인 행 수를 "(표에서 센 수)"로 넣는다(v1.1).
- 진행 현황 탭: `assignments[]`의 state별 행 수를 표시 집계로 보여 준다(예: "최종 확정 8 · 관리자 평가 작성 중 3 · … (표에서 센 수)"). 점수·등급 집계는 만들지 않는다.

### 8.5 평가자 재배정 (`PUT /evaluations/{id}/reviewer {reviewerId}`)
```
┌ 평가자 변경 — 가상사원002 (DEMO002) ─────────────────────┐
│ 현재 평가자: 가상관리자 (ADMIN001) · 평가서 상태 [관리자 평가 작성 중] │
│ 새 평가자 *  [선택 ▾]   〈후보 출처 G-6〉                     │
│ ⚠ 평가자를 바꾸면 기존 평가자가 작성하던 관리자 평가 초안(점수·코멘트)이 │
│   삭제됩니다. 관리자 평가 작성 중이던 평가서는 '자기평가 제출' 상태로     │
│   돌아가고, 새 평가자가 처음부터 작성합니다. 대상자의 자기평가는 그대로  │
│   유지됩니다. 기존 평가자는 즉시 이 평가서를 볼 수 없게 됩니다.         │
│ [ ] 관리자 초안이 삭제됨을 확인했습니다                             │
│                                   [취소] [평가자 변경]          │ danger-solid
└──────────────────────────────────────────────────────────┘
```
- 경고 블록은 상태에 따라 나눈다.
  - `MANAGER_DRAFT`: 위 문구 전체 + 확인 체크박스.
  - `SELF_DRAFT`·`SELF_SUBMITTED`: "아직 관리자 평가 초안이 없을 수 있습니다. 혹시 남아 있는 관리자 초안은 삭제됩니다. 평가서 상태는 그대로 유지됩니다." 체크박스 없음, 버튼 primary.
  - 이유: 계약상 SELF_SUBMITTED도 초안이 초기화될 수 있는데(저장 후 상태가 바뀌지 않는 경우), 초안이 있는지 알 방법이 없다. 그래서 짧은 주의 문구는 항상 둔다.
- 결과:
  - 200 → 요약 갱신, success "평가자를 변경했습니다."
  - 409 EVALUATION_STATE_CONFLICT → "이미 최종 확정된 평가서라 평가자를 바꿀 수 없습니다."
  - 409 EVALUATION_CYCLE_CLOSED → "종료된 주기라 평가자를 바꿀 수 없습니다."
  - 403 → "대상자 본인을 평가자로 지정할 수 없습니다."
  - 409 EVALUATION_REVIEWER_INVALID → §8.3 문구
  - 모든 오류 후 재조회.
- 진입: §8.4 대상·평가자 탭의 [평가자 변경]이다. 요청 경로에 `assignments[].evaluationId`(v1.1)를 쓰고, 본문은 `{reviewerId}`다.
- 결과 처리: 응답은 "갱신 요약"이다. 그래도 표는 주기 상세(`GET /evaluation-cycles/{id}`)를 다시 조회해 참조형으로 다시 그린다. 오류가 나도 같다.
- 모달의 "현재 평가자"와 "평가서 상태"는 요약 행의 `reviewer`·`state`를 쓴다.

### 8.6 내 평가 (`GET /evaluations/me`, `GET /evaluations/assigned`)
```
홈 / 내 업무 / 내 평가
[내 평가] [내가 평가할 사원 (assigned 1건 이상일 때)]

합성 2025 하반기       [평가 진행 중][미완료]      [보기]

- "내가 평가할 사원" 탭: 대상 `이름 (사번)`, 상태, [평가하기](SAVE_MANAGER 있음) 또는 [보기].

### 8.7 자기평가 작성 (본인, `PUT /evaluations/{id}/self`, `POST …/self/submit`)
```
합성 2026 하반기 · 자기평가   [자기평가 작성 중]
기간 2026-07-01 ~ 2026-12-31 (표시용) · 임시저장 후 이어서 작성할 수 있습니다.
ⓘ 제출하면 수정·회수할 수 없습니다.
┌ 1. 업무 수행 ─────────────────────────────────┐
│ 점수 *  ( )1 ( )2 ( )3 (●)4 ( )5      radiogroup, 각 "n점" │
│ 코멘트 (선택)  [                        ] 0/1000자  │
└────────────────────────────────────────────┘
작성 현황: 점수 1 / 2 항목 (표에서 센 수)
마지막 저장 {서버 응답 시각 〈계약 공백 G-8〉}
                           [임시저장] [제출]       ← SAVE_SELF / SUBMIT_SELF
```
- 점수 척도 설명 문구는 계약에 없어 넣지 않는다. 숫자 1~5와 "1점"~"5점" 라벨만 쓴다.
- 임시저장: 빈 점수·일부 항목도 허용한다(계약). 보낼 때 `answers`는 화면의 **모든 항목**이다(빈 점수는 null, 빈 코멘트는 null). 성공하면 role=status "임시저장했습니다."
- 제출: 모든 항목 점수 1~5가 필수다. 비어 있으면 클라이언트가 "모든 항목의 점수를 선택해야 제출할 수 있습니다 (n개 미입력)."라고 알리고 첫 빈 항목으로 포커스를 옮긴다. 통과하면 확인 모달 "자기평가를 제출합니다. 제출 후에는 수정·회수할 수 없습니다." [취소] [제출](primary).
- 코멘트 `maxlength=1000`. 900자를 넘으면 글자 수를 warning 색으로.
- 저장하지 않은 변경을 두고 떠나면 확인한다.
- 오류:
  - 409 EVALUATION_CYCLE_CLOSED → "평가 주기가 종료되어 저장·제출할 수 없습니다." → 읽기 전용 전환 (작성 중 텍스트는 화면에 남겨 복사 가능)
  - 409 EVALUATION_STATE_CONFLICT → "이미 제출된 평가서입니다. 최신 상태를 불러왔습니다."
  - 400 → fieldErrors는 항목 아래, 그 밖은 상단

### 8.8 공개 전 본인 화면 (SELF_SUBMITTED·MANAGER_DRAFT, 또는 CLOSED 미완료)
```
합성 2026 하반기 · 내 평가   [평가 진행 중]
자기평가를 제출했습니다. 평가자가 평가를 마치면 결과가 공개됩니다.
┌ 내 자기평가 (제출됨, 읽기 전용) ───┐
│ 1. 업무 수행  4점 · 코멘트 …       │
└──────────────────────────────┘
```
- 응답에 `managerAnswers`·`finalScore`·`grade` 키가 없다. **관리자 점수·코멘트·등급 영역을 만들지 않는다**(빈 칸·흐린 자리도 없음).
- 본인 응답 `state`는 SELF_SUBMITTED와 MANAGER_DRAFT를 구분해 준다. 그래도 본인 화면은 둘 다 "평가 진행 중"으로 같게 보인다. 관리자의 작성 시작 여부를 드러내지 않기 위해서다.
- CLOSED + `incomplete=true`면 배지 [미완료]를 붙이고 "평가 주기가 종료되어 최종 확정되지 않았습니다. 결과(점수·등급)는 없습니다."라고 쓴다. SELF_DRAFT였다면 자기평가도 "제출되지 않음"으로 표시한다(저장된 초안 답변 공개 여부는 서버 응답을 따름).

### 8.9 결과 화면 (본인 FINALIZED, 평가자도 같은 틀)
```
합성 2026 하반기 · 결과   [최종 확정]
┌ 최종 결과 ─────────────────────────┐
│ 등급  [S]          최종 점수  4.50    │  grade, finalScore (소수 둘째 자리 고정 표기)
└───────────────────────────────────┘
항목          관리자 점수   관리자 코멘트       자기평가(참고)
업무 수행       5           합성 관리자평가      4
협업           4           —                 4
평가자 가상관리자 (ADMIN001)
ⓘ 최종 점수는 관리자 점수의 평균(소수 둘째 자리 반올림)이며 자기평가 점수는 포함하지 않습니다.
  등급 기준: S ≥ 4.50 · A ≥ 3.50 · B ≥ 2.50 · C ≥ 1.50 · D < 1.50
```
- `finalScore`는 number로 오므로(4.5 등) **표기만 소수 둘째 자리로 맞춘다**(`4.50`). 다시 계산하거나 다시 반올림하지 않는다.
- 등급 기준 안내는 계약 §5.5의 표를 그대로 옮긴 설명이다. 화면이 등급을 판정하지 않는다.
- 등급 배지는 neutral 하나다(§11.6). 자기평가 열은 muted이고 머리에 "(참고)"를 붙인다.
- 항목 이름은 `items`(OPEN 시점 스냅샷)다. 캡션 "평가 항목은 주기 시작 시점 기준입니다." 빈 코멘트는 "—".
- 확정 시각 필드는 계약 DTO에 없다(`〈계약 공백 G-8〉`). 표시하지 않는다.

### 8.10 관리자 평가 작성 (배정 평가자, `PUT /evaluations/{id}/manager`, `POST …/manager/submit`)
```
홈 / 내 업무 / 내 평가 / 내가 평가할 사원 / 가상사원002 (DEMO002)
합성 2026 하반기 · 관리자 평가 — 가상사원002 (DEMO002)   [자기평가 제출]
ⓘ 제출하면 즉시 최종 확정되어 대상자에게 결과가 공개됩니다. 수정·회수·재개방할 수 없습니다.
항목          자기평가(참고)          관리자 점수 *        관리자 코멘트 (0/1000자)
1. 업무 수행   4점 · 합성 자기평가      ( )1 … ( )5         [            ]
                               [임시저장] [제출 · 최종 확정]   ← SAVE_MANAGER / SUBMIT_MANAGER
```
- 데스크톱은 참고 열과 입력 열을 나란히 둔다. 모바일은 항목 카드 안에서 참고 → 점수 → 코멘트 순서로 쌓는다.
- 자기평가가 SELF_DRAFT이면 버튼이 없다(allowedActions가 "조회"). 안내 "대상자가 자기평가를 제출하면 작성할 수 있습니다."
- 제출 확인(440px): "가상사원002 (DEMO002)의 평가를 최종 확정합니다. 확정하면 점수·코멘트·등급이 대상자에게 공개되고 수정·회수·재개방할 수 없습니다." + 확인 체크박스 + [최종 확정](danger-solid).
- 성공하면 §8.9 결과 화면으로 바뀐다. role=status "최종 확정했습니다." (점수·등급은 쓰지 않음)
- 오류:
  - 404 (재배정으로 권한을 잃음) → "이 평가서에 접근할 수 없습니다. 평가자가 변경되었을 수 있습니다." + [내가 평가할 사원으로]
  - 409 EVALUATION_REVIEWER_INVALID → "평가자 자격이 확인되지 않아 처리할 수 없습니다."
  - 409 CYCLE_CLOSED / STATE_CONFLICT → §8.7 문구
  - 403 (자기 결재) → "본인 평가서는 관리자 평가를 할 수 없습니다."
- 대상이 OPEN 뒤 퇴사해도 평가자는 완료할 수 있다(계약). 화면에서 막지 않는다.

## S9. 감사 로그 라벨 (계약 §6)

| action | 라벨 | 대상 표시 |
|---|---|---|
| JOB_TITLE_CREATE / UPDATE / DELETE | 직책 추가 / 수정 / 삭제 | [직책] 이름 · 전후 id·name·description |
| SALARY_SETTING_UPDATE | 급여 설정 변경 | [급여 설정] 사원(metadata.employeeId → 이름 (사번) 표시 출처는 2단계 감사 규칙). 전후 값 없음 — 문구 "금액은 기록하지 않습니다" |
| PAYROLL_GENERATE / RECALCULATE / CONFIRM | 급여 생성 / 재계산 / 확정 | [급여] targetLabel(월) · 전후 status · count |
| EVALUATION_CYCLE_CREATE / UPDATE / OPEN / CLOSE | 평가 주기 생성 / 수정 / 열기 / 종료 | [평가 주기] · 전후 state |
| EVALUATION_SELF_SAVE / SUBMIT | 자기평가 저장 / 제출 | [평가서] · 전후 state |
| EVALUATION_MANAGER_SAVE / FINALIZE | 관리자 평가 저장 / 최종 확정 | [평가서] · 전후 state |
| EVALUATION_REASSIGN | 평가자 변경 | [평가서] · 전후 state · 이전/새 평가자 ID |

- 대상 유형 필터에 JOB_TITLE·SALARY_SETTING·PAYROLL·EVALUATION_CYCLE·EVALUATION을 추가한다. 기존 사원·발령·퇴사 전후 표에 `jobTitle` 행을, 부서 전후 표에 `parentId`(상위 부서) 행을 추가한다.
- 감사에는 금액·점수·코멘트·등급이 없다(계약). 화면도 그런 칸을 만들지 않는다.
- metadata의 ID(employeeId·reviewerId 등)를 이름으로 바꿔 보일 출처는 2단계 감사 화면 규칙을 따른다. 없으면 `ID n`으로 쓴다.

## 13. v1(계약 전 초안) 대비 변경

- **S1**: 계약의 평탄 배열과 화면 조립 규칙을 확정했다. 상태 표시는 `onLeave`로 한다.
- **S2**: 부서 설명 필드와 409 코드 4종 문구를 넣었다. 직속 인원 열은 없앴다.
- **S3**: 정렬·인원 열을 없애고 설명 열을 넣었다.
- **S4**:
  - 부서·직급이 필수라 "변경 체크" 대신 현재 값을 미리 채운다.
  - 이력의 null은 항상 "—"로 쓴다. "없음 → B" 표기와 "퇴사로 해제" 행을 없앴다.
- **S5**: 설정 목록·미설정 필터 화면을 없애고 사원 상세 블록으로 옮겼다(G-3).
- **S6**:
  - 생성·재계산·확정 오류를 계약 code로 연결하고 PAYROLL_BUSY를 추가했다.
  - 확정 알림 문구를 없앴다(계약상 알림 없음). 생성 월 max는 두지 않는다.
- **S7**: 공제를 `deductions[]` 길이대로 그린다. 인쇄·다운로드를 없앴다. 실지급을 맨 위로 올렸다.
- **S8**:
  - 주기 편집을 전체 교체 저장 방식으로 바꾸고 sortOrder를 다시 매긴다.
  - 재배정 상태별 주의 문구를 넣었다(MANAGER_DRAFT → SELF_SUBMITTED).
  - `incomplete` 배지, 결과의 등급 기준 안내, finalScore 두 자리 표기를 넣었다.
  - ADMIN 진행 현황 출처를 공백(G-7)으로 표시했다.
- **S9**: 감사 action·targetType을 계약 코드로 바꿨다.
